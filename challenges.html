1. Workspace migration

We are using databricks in our project and earlier we were usign shared workspace where multiple tenant were using that workspace based on some domain
tag we used to identify cost occured for particular tenant is this and so and so.
But some time it is not good pratice and we decided to use our own workspace.
DevOps created new workspace for us and now we need to migrate all stuffs from old to new workspace.
In Our project mostly external tables used so data stored in ADLS is not an issue.
Action Item we took care for new workspace migration are below.

1. Create new metasore table in new workspace which will point to existing ADLS location.
2. Update URL in linked service for databricks as all four environments url are differet.
3. We updated new databricks url in UBS deployement page where it puts jar to new workspace location i.e. dbfs:/Filestore/jars/ourJarname.jar
4. We also need to run GRANT statement in new workspace so that it will give rights on new metastore tables to all existing consumers.

3. Linked service configuration

Actually in our project we are usign databricks resource which was createing job cluster and taking resource from node pool. We are calling our pipeline from ADF and in ADF we have used linked service with min and max worker pool configuration so that our large pipeline will run on bug linked servie and small pipeline will run on small linked service.

Chellenge

Main thing which I observed is our data was not huge for many pipeline but still we are allocating min 2 to max 5 worker. So in real it will not use resource if not requiured but I have checked spark UI and resouce allocation so many time it was adding worker for very small time and then removing which was not required. After analysing it I downgrade many small pipeline to min 1 to max 2 worker so that it can only take minimum resource. even there is no option for only min 1 and max 1 in ADF to databricks so we have to go with that. By using this approach we also saved a lot of cost.

4. Vaccume, Optimize

Table size is increase day by and time travel is also increasing table version as well so we have introduce this new pipline which will run on weekend. and it will run based on configuration and it will vaccume table based on configuration. We are also running optimized command so that all small file merged into big file. VACUUM esg_curated_db.climate RETAIN 168 HOURS OPTIMIZE esg_curated_db.climate; ANALYZE TABLE esg_curated_db.climate COMPUTE STATISTICS FOR COLUMNS esg_entity_id, order_date;

5. Approach modify and boost our pipeline from 5 hours to 30 min

Actually our all pipeline are based on raw i.e. acquisition where this is seperate team and ingesting all data into raw zone. and all pipeline are running on full file, i.e. every day when file come it will have full data, not only delta , let say yesterday file ingested and it was having 1000 records and today it have 1100 records where we are running merge so 100 will be inserted new record and 1000 will be updated if key matched so we are checking if any change is there then we will udpate if not then we will ignore. we are also ignoring technical columns in compare. So this file ingestion will have process id which is feed id + current time stamp epoch id. so every day it will have different proess id. For all pipeline we are getting max(process_id) from raw zone so that we will get latest records. But scenario is different for this pipeline. In this case file and records are huge so at acquisition side they are also splitting this file into multiple file and then uploading or ingesting. so at raw side we would have multiple process id for same day. we can not use max process id if we will use this then it will end up with partial records. So this pipeline was already working on business date pattern, i.e. it was checking and getting data of max businessdate and that businessdate was not partition column. This pipeline was taking more and more time.

Solution

I was checking query and quesry itself was taking all time other part was very quick so I updated this with process id instead of business date but we can not simpley take max process id. In our project process_log table was already there so we are inserting entry into this table I also leverage this. Once pipeline processed then at last we are inserting entry into this table with max process id. when next run would start then we are getting entry from this table and taking all process id greather than this process id so by doing this we will get multiple process id. and I also adding dedupling logic in query which window partition on business key , order by desc and rn=1 so even we do have multiple entry we will get one. With this Fix pipeline was running very quick and less than 30 minute. and I haved a lot of cost.
