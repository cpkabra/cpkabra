01

Databricks Workspace Migration

Migrating workspace configuration without moving underlying data

Databricks Unity Catalog / Metastore ADLS Azure Data Factory Deployment Automation

Business Context

Our project initially used a shared Databricks workspace where multiple tenants operated within the same environment. We used domain-specific tags to identify and allocate cloud costs to individual tenants.

As the project evolved, we decided to move to a dedicated workspace to improve isolation and simplify resource and environment management. DevOps provisioned the new workspace, and we needed to migrate the existing configuration and dependencies.

Most of our tables were external tables, with their data stored in Azure Data Lake Storage (ADLS). This meant the underlying data did not need to be physically moved; instead, we needed to configure the new workspace to access the existing locations.

Migration Activities

  1. Re-create the required metastore and external table definitions in the new workspace, pointing to the existing ADLS locations and configuring the required catalog and storage access.
  2. Update the Databricks URLs in the Azure Data Factory linked services for all four environments.
  3. Update the Databricks workspace URL in the UBS deployment configuration so that the JAR is deployed to the correct workspace location, such as dbfs:/FileStore/jars/ourJarname.jar where supported by the workspace configuration.
  4. Execute the necessary GRANT statements to restore the required privileges for existing consumers of the migrated tables.
Challenge encountered

We combined the workspace migration with a regular application release. This increased deployment risk and resulted in two expedited releases on the same day. Additionally, the production and UAT linked services still referenced an outdated workspace URL because DevOps had provisioned a replacement workspace after encountering issues with the original one.

Solution & Preventive Improvement

We introduced a validation utility to verify environment-specific parameter files before deployment.

  • Deploy the parameter files using an environment-aware configuration, starting with DEV.
  • Validate that all environment-specific parameters, including workspace URLs, are present and correct.
  • Verify the configuration before promoting the deployment through UAT and PROD.
  • Keep workspace migration changes separate from regular application releases wherever possible.
Key Engineering Lesson

Validate configuration across every environment and use a controlled promotion process. Successful code deployment does not guarantee that environment-specific dependencies are correct.

Azure Cloud Cost Optimization

Investigating unexpected daily spend and reducing idle SQL Warehouse runtime

Azure Cost Management Databricks SQL Warehouse Auto Stop FinOps Cost Analysis

Problem

I was asked to review our existing cloud usage and identify opportunities to reduce costs. The project is divided into two tenants: ESG and XREF. XREF has around 10 pipelines that use approximately 5 hours of compute daily, while ESG has around 25 pipelines that use approximately 17 hours daily. However, the cost attributed to XREF was higher than ESG, which did not align with the expected workload.

A daily cost review showed that XREF was generating approximately $55 per day, including weekends, even though its pipelines do not run on weekends. This suggested that a resource outside the scheduled pipeline runs was continuing to consume compute.

I filtered Azure Cost Management data by day and identified a Databricks SQL endpoint (SQL Warehouse) that was running continuously. The cost was present in UAT and PROD, while the corresponding resource was stopped in DEV and TEST.

Operational constraint

A consumer used the SQL endpoint to access data through an API and needed the data to be available quickly. When the endpoint was stopped, the first request could take approximately 5–7 minutes while the endpoint started. Keeping it running continuously improved responsiveness but increased unnecessary cloud expenditure during idle periods.

Solution

I reviewed the usage with the consuming team and proposed enabling inactivity-based auto-stop in UAT. We agreed to configure the SQL Warehouse to stop after 45 minutes of inactivity. If it continues to be used, the inactivity timer resets and the warehouse remains available.

  • Compared daily cloud costs across ESG and XREF and investigated the unexpected cost difference.
  • Filtered Azure Cost Management data by day to identify the resource responsible for weekend spend.
  • Compared resource states across DEV, TEST, UAT, and PROD.
  • Agreed on a 45-minute inactivity auto-stop in UAT with the consuming team to balance cost and access needs.
  • Identified and implemented optimization opportunities across project environments.
Outcome

The cloud cost review and optimization work delivered approximately $15,000 in annual savings across all project environments. The UAT auto-stop setting reduced avoidable idle runtime while preserving the ability to restart the warehouse when required. The before-and-after Azure Cost Management data can be used to validate the realized savings.

Databricks Linked Service & Cluster Sizing

Right-sizing compute for large and small ETL workloads

Azure Data Factory Databricks Job Clusters Node Pools Spark UI Resource Allocation

Architecture

Our ETL pipelines are orchestrated through Azure Data Factory (ADF), which invokes Databricks jobs. The Databricks jobs use compute provisioned through the configured node pools and cluster settings.

We maintained different linked service configurations with minimum and maximum worker counts so that larger pipelines could use more compute, while smaller pipelines could operate with fewer resources.

What I observed

Some relatively small pipelines were configured with a minimum of two workers and a maximum of five. Using the Spark UI and resource-allocation information, I observed that some jobs briefly scaled up and subsequently removed workers even though their workloads did not justify the extra capacity.

Solution

  • Analyzed the Spark UI and execution patterns to understand the actual compute requirements of individual pipelines.
  • Reduced the minimum worker count from two to one for suitable smaller pipelines.
  • Reduced the maximum worker count from five to two for these workloads.
  • Kept larger workloads on configurations that provided sufficient parallelism and processing capacity.

Our ADF linked service configuration did not provide a convenient way to enforce exactly one worker for the relevant setup, so we used a minimum of one and a maximum of two workers instead.

Outcome

Better alignment between workload size and allocated compute, reducing unnecessary resource consumption and helping lower Databricks costs without applying the same cluster size to every pipeline.

Delta Lake Maintenance: VACUUM, OPTIMIZE & ANALYZE

Managing table storage, file layout, and query performance

Delta Lake VACUUM OPTIMIZE ANALYZE TABLE Scheduled Maintenance

Problem

As our Delta tables received repeated updates and merges, their storage footprint increased and additional data files accumulated. We also needed to manage historical versions and maintain statistics to help the query optimizer make better decisions.

To address this, we introduced a configuration-driven maintenance pipeline scheduled to run over the weekend. The pipeline identifies the configured tables and executes the appropriate maintenance operations.

Maintenance Commands

Databricks SQL
-- Remove eligible obsolete data files
VACUUM esg_curated_db.climate
RETAIN 168 HOURS;

-- Compact small files into larger files
OPTIMIZE esg_curated_db.climate;

-- Refresh optimizer statistics for selected columns
ANALYZE TABLE esg_curated_db.climate
COMPUTE STATISTICS FOR COLUMNS
esg_entity_id, order_date;

What Each Command Does

  • VACUUM: Removes eligible unreferenced data files older than the specified retention period. It does not simply remove old Delta transaction-log versions. The retention period must be selected carefully to preserve required recovery and time-travel capabilities.
  • OPTIMIZE: Rewrites eligible data files to improve file layout and compact small files. This can improve read performance by reducing file-management overhead.
  • ANALYZE TABLE: Computes statistics used by the query optimizer to help select efficient execution plans. Column statistics can be especially useful for joins and filters.

Implementation Approach

  • Maintain a configuration-driven list of target tables.
  • Schedule maintenance during a suitable low-activity window.
  • Apply retention settings according to recovery requirements.
  • Monitor execution duration, file counts, storage usage, and query performance to evaluate the impact.
Important Consideration

VACUUM, OPTIMIZE, and ANALYZE serve different purposes. Their schedules and configurations should reflect data volume, query patterns, retention requirements, and operational cost.

Pipeline Optimization: From 5 Hours to Under 30 Minutes

Replacing an expensive business-date scan with incremental process tracking

Apache Spark Delta Lake MERGE Incremental Processing Window Functions Query Optimization

Existing Data Processing Pattern

Our pipelines consume data from the raw or acquisition layer, which is maintained by a separate ingestion team. Most incoming files contain full snapshots rather than only changed records.

For example, yesterday's file might contain 1,000 records, while today's file contains 1,100 records. Our merge logic inserts new records and updates existing records when their business attributes have changed. Technical columns are excluded from change comparisons.

Each ingestion batch is assigned a process ID derived from the feed ID and the current epoch timestamp. In the normal pipeline pattern, we select the latest process ID to identify the latest batch.

Why the existing approach failed

The pipeline under investigation processed a very large dataset. To manage ingestion, the acquisition team split the input into multiple files, creating multiple process IDs for the same business date. Selecting only MAX(process_id) would therefore retrieve an incomplete subset of the day's data.

Original Processing Bottleneck

The pipeline used a business-date-based approach to identify records for processing. The business-date column was not a partition column, and the query required considerable time to locate and process the relevant records.

I investigated the query execution and found that the data retrieval query itself accounted for most of the runtime, while the other pipeline steps were comparatively fast.

Solution: Incremental Process-ID Tracking

Instead of selecting the maximum process ID directly from the raw table, I leveraged the existing process-log table to track the last successfully processed process ID.

  1. Read the last successfully processed process ID from the process-log table at the beginning of the pipeline.
  2. Retrieve all eligible process IDs greater than the last processed ID, ensuring that every ingestion batch for the relevant processing window is considered.
  3. Process records across the selected process IDs rather than selecting only the single maximum process ID.
  4. Apply deduplication using a window function partitioned by the business key and ordered by the relevant timestamp or process sequence in descending order.
  5. Retain only the latest eligible record for each business key before applying the merge logic.
  6. Update the process log only after the batch has been processed successfully, so the next execution can continue from the correct checkpoint.

Illustrative Deduplication Logic

The following example illustrates the windowing approach. Replace the sample table and column names with those used in your actual pipeline.

Spark SQL
WITH eligible_records AS (
    SELECT *
    FROM raw_table
    WHERE process_id > last_processed_id
),
ranked_records AS (
    SELECT *,
        ROW_NUMBER() OVER (
            PARTITION BY business_key
            ORDER BY process_id DESC, updated_at DESC
        ) AS rn
    FROM eligible_records
)
SELECT *
FROM ranked_records
WHERE rn = 1;

Note: The example uses last_processed_id as a placeholder for the checkpoint retrieved from the process log. In production, checkpoint handling should also account for failed batches, concurrent runs, late-arriving data, and deterministic ordering when records have the same process ID.

Performance Improvement

5 hours → under 30 minutes
By improving incremental data selection and introducing deduplication before downstream processing, the pipeline's execution time dropped from approximately five hours to less than thirty minutes. This represents a runtime reduction of more than 90%, along with a substantial opportunity to reduce compute consumption.

Run Pipelines Only When Upstream Data Is Available

Using event-informed marker files to avoid unnecessary pipeline runs and reduce compute contention

Azure Data Lake Storage Kafka Events Marker Files Pipeline Orchestration Compute Optimization

Problem

Several pipelines perform full loads and then check whether upstream data has changed. If no changes are found, the pipeline completes without updating the SCD Type 2 history, but it still consumes compute. The Acquisition team uploads files to the raw-zone container, and some upstream feeds arrive weekly, monthly, or on an ad hoc basis rather than every day.

In one pipeline pattern, a master pipeline runs for approximately 45 minutes before starting its child pipeline. The child then checks whether raw data has changed. If there is no new data, the work produces no useful update. This can waste close to one hour of compute per run; around five pipelines follow this pattern.

Operational constraint

Pipelines were scheduled because multiple pipelines could run at the same time and compete for limited compute resources. Running every pipeline daily, even when its upstream files had not changed, wasted compute; but removing the schedule without an alternative trigger could make it harder to coordinate execution and avoid resource contention.

Solution: Marker File Strategy

We used events emitted by the Acquisition team after file uploads. A consumer reads the relevant Kafka topic and, when an upload is detected, writes a marker file to a designated folder in the data lake. At its scheduled execution time, the pipeline checks that folder and starts the master and child pipelines only when a relevant marker exists. After the child pipeline completes, the marker is moved to an archive folder.

  • Listen to the relevant Kafka topic for upstream file-upload events.
  • Create a marker in the current-trigger folder when a relevant file has arrived.
  • At the configured run time, check for the pipeline's marker before starting the master and child pipelines.
  • After successful child-pipeline execution, move the processed marker into the archive folder.
  • Use separate marker names to associate each upstream feed with its intended pipeline.
Example marker file paths
-- Current trigger markers
pipeline-trigger/am-currentfiles-xyz1.trg
pipeline-trigger/am-currentfiles-xyz2.trg
pipeline-trigger/am-currentfiles-xyz3.trg
pipeline-trigger/ubspasi-currentfiles-abc1.trg

-- Archived markers after processing
pipeline-trigger/am-archivefiles-xyz1.trg
pipeline-trigger/am-archivefiles-xyz2.trg
pipeline-trigger/am-archivefiles-xyz3.trg
pipeline-trigger/ubspasi-archivefiles-abc1.trg
Outcome

The marker-file approach allows pipelines to check for upstream availability before launching expensive master and child processing. It reduces avoidable runs when no new data has arrived and helps manage compute usage more deliberately. The actual compute savings can be measured by comparing run counts and compute duration before and after introducing the strategy.

Key Takeaways

Engineering principles I applied

  • Configuration management: Validate environment-specific parameters before promoting deployments.
  • Cost awareness: Use actual utilization and cost data to identify opportunities for optimization.
  • Right-sized compute: Match worker allocation to workload requirements rather than using a uniform configuration for every pipeline.
  • Delta Lake maintenance: Use VACUUM, OPTIMIZE, and ANALYZE for their distinct storage and query-optimization purposes.
  • Incremental processing: Track successfully processed data with reliable checkpoints and deduplicate records before downstream operations.
  • Upstream-aware orchestration: Use upload events and marker files to avoid starting pipelines when no new source data is available.
  • Measure the outcome: Use runtime, resource utilization, and cloud-cost metrics to validate improvements.
